# Daytona BYOC on GCP — Deployment Guide

> **Kubernetes-only.** BYOC is deployed exclusively onto a Kubernetes cluster
> (GKE / EKS / AKS) using the [`daytona-region`](../../charts/daytona-region)
> Helm chart. The chart deploys the **runner as a DaemonSet inside the
> cluster** — there is no separate-VM runner path. The canonical install is
> `helm install daytona-region ./charts/daytona-region/`; see
> [`charts/daytona-region/QUICKSTART.md`](../../charts/daytona-region/QUICKSTART.md)
> for the end-to-end walkthrough.
>
> This directory is **operator-side IaC** for a BYOC deployment
> on Google Cloud (GKE Standard): [`up.sh`](./up.sh) provisions the cluster,
> object storage, ingress, and TLS, then helm-installs the chart. The
> deprecated bare-metal GCE/VM setup is segregated under
> [`.legacy/`](./.legacy/) and is not part of this flow.

This guide walks through deploying **BYOC** on
Google Cloud. The goal is to ship a working end-to-end deployment AND make the
friction points concrete.

## What BYOC actually is

With BYOC you use **Daytona Cloud** (`app.daytona.io`) as the control
plane but run the underlying **compute** in your own GCP project. You do
this by creating a custom *region* on your own **GKE** cluster. The
`daytona-region` chart brings up the whole region — proxy, snapshot-manager,
ssh-gateway, the `runner-manager`, and the **runner DaemonSet** — and a
pre-install hook registers the region with Daytona Cloud.

```
         ┌─────────────────────────────────────────────────────────┐
         │                 Daytona Cloud (app.daytona.io)          │
         │  - Dashboard, API, auth, snapshot index, billing        │
         │  - Knows about your custom region by name + proxyUrl    │
         └────────────────────────┬────────────────────────────────┘
                                  │ HTTPS (outbound only:
                                  │  region registration,
                                  │  runner-manager heartbeats)
                                  ▼
   ┌───────────────────────────────────────────────────────────────┐
   │  Your GKE cluster  (daytona-region chart)                     │
   │                                                               │
   │   ┌──────────┐  ┌─────────────────┐  ┌────────────────────┐   │
   │   │  proxy   │  │ snapshot-manager│  │   runner-manager   │   │
   │   └──────────┘  └─────────────────┘  └────────────────────┘   │
   │                                                               │
   │   ┌───────────────────────────────────────────────────────┐  │
   │   │  runner DaemonSet  (one pod per sandbox-labelled node) │  │
   │   │  - daytona-runner runs HERE, in-cluster               │  │
   │   │  - Docker + Sysbox bootstrapped on the node           │  │
   │   │  - sandbox containers run on these nodes              │  │
   │   └───────────────────────────────────────────────────────┘  │
   │                                                               │
   │   ingress-nginx (cloud LB)   +   cert-manager (wildcard TLS)  │
   └───────────────────────────────┬───────────────────────────────┘
                                  ▼
                       ┌─────────────────────┐
                       │  GCS bucket (yours) │
                       │  - snapshot blobs   │
                       │  - builder context  │
                       └─────────────────────┘
```

Daytona Cloud routes your SDK calls (or dashboard actions) through
your proxy (running in GKE), which forwards them to a runner pod on
a sandbox node, which runs the actual sandbox container on that same node. The
snapshot-manager and every runner pod read and write the same GCS bucket you
own via the **GCS interop XML API** using HMAC keys — so the chart's
S3-only snapshot-manager works unmodified.

## Secret handling

**No secret is ever passed on a command line, written to a long-lived disk
file, or echoed to a log.** Storage credentials (GCS HMAC keys) and the
Daytona API key are rendered into a values file kept only in `.state/` (mode
0600) and consumed by `helm install`; the chart writes them into Kubernetes
Secrets, which GKE encrypts at rest.

What that means in practice:

- **HMAC access / secret keys**: generated by `up.sh` via
  `gcloud storage hmac create`, saved 0600 to `.state/hmac.env`, and rendered
  into the helm values. The chart stores them in the runner Secret and the
  snapshot-manager Secret — both halves point at the same bucket.
- **DAYTONA_API_KEY** (your *org* key): prompted for at runtime,
  written into the rendered values file (0600), and handed to the chart's
  registration hook, which stores it in a Kubernetes Secret.
- **CLOUDFLARE_API_TOKEN** (if you use Cloudflare for DNS-01): handed to
  cert-manager once via a Kubernetes Secret (encrypted at rest by GKE).

The `.state/` directory holds prompt answers, resource names, and the rendered
values — treat any file containing HMAC or API-key material as a secret.

## Deployment steps

Even with this guide automating most of it, these are the actual decisions and
actions involved.

| # | Step | Automated by this repro? |
|---|---|---|
| 1 | Sign up at daytona.io | ❌ Interactive web flow |
| 2 | Create an organization | ❌ Dashboard click |
| 3 | Generate a personal API key at `app.daytona.io/dashboard/keys` | ❌ Manual; the BYOC docs don't link to this page |
| 4 | Pick a region name (lowercase, alphanumeric + `.-_`) | ✅ Defaults to the cluster name |
| 5 | Pick a proxy URL (FQDN you own) | ✅ Derived as `proxy.<BASE_DOMAIN>` |
| 6 | Set up GCS bucket + HMAC keys for snapshots + builder | ✅ `gcloud storage buckets create` + service account + HMAC key |
| 7 | Provision the GKE **Standard** cluster (not Autopilot) | ✅ `gcloud container clusters create` |
| 8 | Add a sandbox node pool (labelled + tainted for runner pods) | ✅ `gcloud container node-pools create` |
| 9 | Point DNS at the cluster's LB IP | ✅ Records printed; you create the A records |
| 10 | Install ingress-nginx (cloud-LB-backed) | ✅ helm |
| 11 | Install cert-manager + ClusterIssuer for wildcard TLS | ✅ DNS-01 |
| 12 | Install `daytona-region` chart — registers the region AND brings up proxy + snapshot-manager + runner-manager + **runner DaemonSet** | ✅ `helm install` |
| 13 | Wait for runner pods to schedule on the sandbox nodes | ✅ `kubectl -n daytona get pods` |
| 14 | Validate with the SDK / dashboard | ✅ `e2e.sh` runs `daytona.create(target=<region>)` |

## Common pitfalls

Each of these is real and surfaces during a BYOC deployment.

1. **Runner pods only schedule on labelled, tainted nodes.**
   The chart's runner DaemonSet uses `nodeSelector: daytona-sandbox-c=true`
   and tolerates the `sandbox=true:NoSchedule` taint. If your cluster has no
   node carrying that label *and* taint, the runner pods stay `Pending`, the
   region shows "no available runners", and `daytona.create(target=region)`
   fails. `up.sh` creates a dedicated `daytona-sandbox` node pool for exactly
   this reason.

2. **The declarative builder needs storage credentials wired up in two places, not one.**
   The snapshot-manager gets its credentials from
   `services.snapshotManager.storage.s3.*` in helm values. The runner pods
   ALSO need `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_DEFAULT_BUCKET`/
   `AWS_REGION`/`AWS_ENDPOINT_URL` (yes — `AWS_*`, even on GCP; the runner
   binary uses an S3 client) under `services.runner.env`. They must point at
   the same bucket. If they don't, snapshot creation via
   `Image.debian_slim(...).pip_install(...)` fails with a 403 at the
   inspect/build step. This chart renders both halves from the same values.

3. **GCS HMAC keys are per-service-account, but Daytona expects AWS-shaped
   env vars.** The clean path is: create a dedicated service account, mint
   HMAC keys for it, grant it `roles/storage.objectAdmin` on the bucket,
   point `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` at those keys, and
   set `AWS_ENDPOINT_URL=https://storage.googleapis.com`. This repro does
   exactly that.

4. **Two different `dtn_xxx` API keys.** The *org* key is what the
   chart uses to register the region (`daytonaApiKey`). The *runner* key is a
   separate credential the `runner-manager` uses to register runners with
   Daytona Cloud; the registration hook writes it into
   `<release>-daytona-region-runner-manager-api-key`. Both look identical
   (`dtn_...`), so it's easy to use the wrong one — the org key in the
   runner-manager slot (or vice versa) fails silently.

5. **The runner runs in-cluster as a DaemonSet — there is no GCE/VM step.**
   The `daytona-region` chart deploys `daytona-runner` as a privileged
   DaemonSet pod on each sandbox-labelled node; a `docker-installer` sidecar
   bootstraps Docker + Sysbox on the node via `nsenter`, and a
   `daytona-binary-installer` sidecar pre-stages the sandbox binaries onto the
   node. Sandbox containers then run on those same GKE nodes. (The deprecated
   separate-VM path lives under [`.legacy/`](./.legacy/) for forensic
   comparison only.)

6. **The wildcard proxy URL needs DNS-01 TLS.** `proxy.example.com` and
   `*.proxy.example.com` must both have a trusted cert. HTTP-01 doesn't
   cover wildcards, so you need DNS-01, so you need an API token for your
   DNS provider (e.g. Cloudflare).

7. **Re-running registration is fragile.** The registration hook is
   idempotent only up to a point: it skips when the region-config Secret
   already exists, but a half-registered region (e.g. snapshot-manager
   credentials missing) forces a regenerate path. If you change `regionName`
   or `proxyUrl` after the first install, the hook will try to register a
   *new* region rather than update the old one. Clean up stale regions in
   Daytona Cloud before re-running.

8. **`helm uninstall` does NOT clean up Daytona Cloud state.** The region
   you registered stays in Daytona Cloud's database. You have to call the
   API or visit the dashboard. The `teardown.sh` script in this repo handles
   the GCP-side cleanup; the region must still be removed from Daytona Cloud.

## Capacity sizing

Sandbox capacity is a function of how many sandbox-labelled nodes you run and
how large they are. The runner DaemonSet places one runner pod per
sandbox-labelled node, and sandbox containers run on those nodes.

- Add capacity by scaling the sandbox node pool (more nodes) or using a larger
  machine type. `up.sh` queries your CPUS quota in `$GCP_REGION` and offers a
  menu of machine types that fit.
- With 2× CPU over-provisioning, ~64 vCPU of sandbox-node capacity is roughly
  enough for ~16 sandboxes at 4 vCPU / 4 GiB each.
- `up.sh` provisions a small default pool to keep the repro cheap; resize the
  `daytona-sandbox` node pool for production-shape capacity.

## What this setup requires

| Thing | Where it comes from |
|---|---|
| `DAYTONA_API_KEY` | Generate at https://app.daytona.io/dashboard/keys (the org key) |
| Base DNS domain | A domain/subdomain you own (e.g. `byoc.yourdomain.com`); A records point at the cluster LB IP |
| Let's Encrypt email | Anything — used for ACME registration |
| DNS-01 provider token | e.g. a Cloudflare "Edit zone DNS" token scoped to your zone, for wildcard TLS |

| `gcloud` auth | `gcloud auth login` AND `gcloud auth application-default login`. The principal needs Owner or a combination of: roles/container.admin, roles/storage.admin, roles/iam.serviceAccountAdmin, roles/iam.securityAdmin, roles/serviceusage.serviceUsageAdmin. |
| CLIs installed locally | `gcloud`, `kubectl`, `helm`, `jq`, `envsubst`, `yq` |

## How to run

```bash
cd <your helm-charts checkout>

# GCP auth - both required
gcloud auth login
gcloud auth application-default login

# Single interactive bring-up: GKE Standard + sandbox node pool + GCS/HMAC
# + ingress-nginx + cert-manager + helm install daytona-region.
# (~20-30 min: ~10 min GKE, ~5 min cert issuance, runner pods schedule after install)
bash scripts/gcs-setup/up.sh
```

`up.sh` prompts for the cluster name, base domain, region name, Let's Encrypt
email, Daytona Cloud API URL + admin key, GCP project/region and GCS bucket
(answers are saved 0600 to `.state/prompts.env` and reused on re-run). The
runner image is not prompted for; it follows the chart appVersion.

After it completes:

```bash
# Smoke test: daytona.create(target=region) then code_run("print('Hello World')")
bash scripts/gcs-setup/e2e.sh

# When done (GCP-side cleanup; region must still be removed from Daytona Cloud):
bash scripts/gcs-setup/teardown.sh
```

## Verifying the install

Once `up.sh` finishes:

```bash
# GKE nodes Ready, sandbox node pool present
kubectl get nodes -L daytona-sandbox-c

# ingress LB IP assigned
kubectl -n ingress-nginx get svc ingress-nginx-controller

# Region resources up: proxy, snapshot-manager, runner-manager, runner pods
kubectl -n daytona get pods

# Certificates Ready (proxy + wildcard, snapshot-manager)
kubectl -n daytona get certificate

# Runner pods are 2/2 Running on each sandbox node; the binary-installer
# should report it pre-staged the sandbox daemon binary onto the node:
kubectl -n daytona logs -l app.kubernetes.io/component=runner \
  -c daytona-binary-installer --tail=20

# Region registered in Daytona Cloud
curl -sS -H "Authorization: Bearer $DAYTONA_API_KEY" \
  https://app.daytona.io/api/regions | jq '.[] | {name, id, proxyUrl}'

# Runners report 'ready' in Daytona Cloud (after runner-manager registers them)
curl -sS -H "Authorization: Bearer $DAYTONA_API_KEY" \
  https://app.daytona.io/api/runners | jq '.[] | {id, name, state, score:.availabilityScore}'
```

## GCS-specific quirks that this repro handles

- **No Uniform Bucket-Level Access (UBLA).** GCS UBLA rejects any request
  bearing an `x-amz-acl` header with HTTP 400 InvalidArgument. Daytona's
  snapshot-manager (built on `docker/distribution` v2 with the S3 storage
  driver) always sends `x-amz-acl: private` when initiating a multipart
  upload. So if UBLA is enabled, every `docker push` of a layer larger
  than ~5 MB (which is most layers) fails. The script deliberately
  creates the bucket WITHOUT `--uniform-bucket-level-access`. PAP
  (public-access prevention) stays on — it only blocks PUBLIC ACLs, not
  the private one the snapshot-manager sends, so it's compatible.
- **HMAC interop credentials, not IAM.** GCS exposes an S3-compatible
  endpoint at `storage.googleapis.com` that uses HMAC keys (minted per
  service account). The chart's snapshot-manager and the runner pods' `AWS_*`
  env vars all point at the SAME HMAC keys + bucket, giving us the
  bidirectional read/write the declarative-builder pipeline needs.
- **Bucket region matters.** GCS bucket location must equal the
  `SNAPSHOT_MANAGER_STORAGE_S3_REGION` the chart sends in S3 signature
  headers. The script enforces this by setting both to `$GCP_REGION`.

## Known gaps in this setup

- **No Workload Identity / Workload Identity Federation path.** The
  snapshot-manager and runner use HMAC keys (static credentials). Production
  should use Workload Identity to bind the relevant ServiceAccounts to a GSA
  with `storage.objectAdmin` on the bucket. The chart supports this — see the
  chart README's "S3 Authentication" section. HMAC is used here because the
  runner binary uses an S3 client and needs HMAC-shaped credentials anyway.
- **Single sandbox node pool, default network.** The repro adds one
  `daytona-sandbox` pool in the project's default VPC. Production would use a
  dedicated VPC with private subnets + Cloud NAT and spread sandbox nodes
  across multiple zones.
- **`e2e.sh` does not yet test private-GAR pulls.** It pulls a public image
  and exercises the declarative builder. A private-Artifact-Registry path
  through Daytona's broker is set up by `.legacy/gcr-setup.sh`; test it
  manually via the Daytona dashboard for now.

## Optional: private Artifact Registry for Daytona Cloud

If you want a sandbox in your BYOC region to pull a private image from your own
GCP Artifact Registry (the GCP equivalent of AWS ECR), use the
`gcr-setup.sh` helper under [`.legacy/`](./.legacy/). It provisions an
Artifact Registry repository in `$GCP_REGION`, a dedicated
minimal-privilege service account (`roles/artifactregistry.reader` scoped to
that one repo), and a JSON key you paste into Daytona's dashboard registry
form. Private-registry auth is brokered centrally by the Daytona control plane
on every pull — the runner never holds those credentials itself.

```bash
export GCP_PROJECT='your-project'
export GCP_REGION='us-central1'   # match what you used for up.sh
bash scripts/gcs-setup/.legacy/gcr-setup.sh
```

You'll get output you can paste into
`https://app.daytona.io/dashboard/registries` → 'Add Registry' (Registry URL
`<region>-docker.pkg.dev`, username `_json_key`, password = the JSON key).
Image references in sandboxes then use
`<region>-docker.pkg.dev/<project>/<repo>/<image>:<tag>`. Re-print the key
with `--show-key`, rotate with `--rotate-key`, or remove with `--teardown`.

## When you've finished running it

You will have:
1. A working BYOC region on GKE, with the runner DaemonSet scheduling runner
   pods onto your sandbox nodes
2. Working SDK calls targeting your custom region
3. Working declarative builder snapshot creation (the runner's `AWS_*` env
   vars point at the same GCS bucket the snapshot-manager uses)
4. Direct experience with the pitfalls listed above

You can then either tear down (cheapest), keep it running to demo, or iterate
as you experiment.

## Manual cleanup that teardown.sh CANNOT do

`teardown.sh` cleans up the GCP resources programmatically. A few things
cannot be automated and require action in
[app.daytona.io](https://app.daytona.io):

1. **The region in Daytona Cloud.** `helm uninstall` (and thus `teardown.sh`)
   does not deregister the region — remove it via the dashboard or the
   `DELETE /api/regions/<id>` endpoint.
2. **The user/organization that owns the region.** Removing this is a
   privileged dashboard action — there's no API.
3. **Personal API keys.** Rotate or revoke at
   https://app.daytona.io/dashboard/keys after each test run if you want
   to be extra safe.

The script prints explicit reminders at the end of `teardown.sh`.
